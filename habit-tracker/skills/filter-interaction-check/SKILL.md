# 筛选交互检查（filter-interaction-check）

## 用途

一句话：**检查一次筛选交互是否"做完整"了——有结果能看、没结果有交代、清空能恢复，且键盘和读屏用户同样可用。**

筛选交互最容易"看起来做完了"：默认状态下数据是全的，界面也好看；用户一点别的标签，列表空掉却没有任何解释，也找不到回头路。本 Skill 专门盯这个缺口。

## 何时使用

- 新增筛选标签 / 分类 chips / Tab 切换 / 列表过滤
- 修改筛选的数据来源、排序、默认值
- 提交前对已有筛选交互做一次回归自查

## 使用方式

1. 定位被检代码四处：筛选 UI 节点、筛选状态变量、渲染函数、事件绑定
2. 逐条过下面的检查清单，每项标 ✅ 通过 / ❌ 不通过 / ⚠️ 未测
3. 只要有一项 ❌ 就是 must-fix：先修，再按同一份清单复查
4. 输出检查记录（格式见文末），追加到项目内的调用记录文件

## 检查清单

### A. 三态完整性（核心）

- [ ] A1 有结果：筛选后列表只显示命中的数据，条数与状态提示一致
- [ ] A2 无结果：出现**明确的空状态文案**，说明"为什么空"，而不是留一片空白
- [ ] A3 无结果时：给**就地恢复入口**（清空筛选 / 看全部），不要逼用户自己猜
- [ ] A4 清空恢复：清空后回到未筛选的完整列表，空状态与筛选提示同时消失
- [ ] A5 筛选状态可见：选中的筛选项有明确视觉标记，并显示"筛了谁 + 命中几条"
- [ ] A6 边界区分：「数据本来就是空的」与「数据有但被筛没了」必须是两种不同文案，不能混用

### B. 作用域与数据

- [ ] B1 筛选只影响目标列表：不污染其他计数、其他板块、其他日期
- [ ] B2 不写坏存储：纯展示态不落盘，或落盘后重载能正确恢复
- [ ] B3 不留"幽灵筛选"：切日期 / 切视图 / 重开弹窗后，筛选标记与列表内容保持一致
      （注意：切到**本身没有数据的日期**时，状态行显示 `0/0 条` 属正常，不要误判为不通过；
      要验的是"状态行与当前日期数据同步"，而不是"一定有条数"）

### C. 可访问性

- [ ] C1 筛选项用原生 `<button>`（可 Tab 聚焦、Enter/Space 触发），不用 div 冒充
- [ ] C2 选中态同步 `aria-pressed`（或用 `role="tab"` + `aria-selected`）
- [ ] C3 筛选组有语义容器：`role="group"` + `aria-label` 说明"这组按钮筛什么"
- [ ] C4 结果变化能被读屏感知：状态提示 / 空状态挂 `role="status"` + `aria-live="polite"`
- [ ] C5 选中态对比度 ≥ 4.5:1（文字色 vs 背景色），深浅主题都要过
- [ ] C6 选中态不只靠颜色：补字重 / 图标之类的非颜色线索
- [ ] C7 恢复入口可被键盘到达，且有可读文案（不要只有一个 "×"）

### D. 回归

- [ ] D1 三种情况各有行为级测试（有结果 / 无结果 / 清空恢复），并断言提示文案
- [ ] D2 全量测试跑通，没有既有用例被破坏

## 记录格式

每次调用追加一条：

```md
## 调用 N · 日期 · 被检对象
- 触发场景：
- 检查结果：✅ x 项 / ❌ y 项 / ⚠️ z 项
- ❌ 明细（must-fix）：编号 + 现象 + 证据
- 处置：改了什么；复查结果
- 结论：
```

## 常见失败模式（本项目真实踩过）

- 复用其他容器的 class 到新容器时，定位类规则不跟着走，必须在新容器下重新声明
- 元素只写了 `id` 没写 `class`，CSS 类选择器不会命中——自检时要确认样式真的生效，而不是"我以为写了"
- jsdom 里对**外层容器** `.click()` 不会触发内层监听（click 不向下冒泡），测试要点真正绑定的那个元素
- 空状态文案与"本来就没数据"的文案混用，用户分不清是自己筛没了还是真没有
