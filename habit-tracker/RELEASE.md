# 自律计划 · 发布清单（RELEASE.md）

- 版本：**v1.0（2026-10-14 建立）** —— 发布清单本身第一天立好，跟着 v1.0 一起走。
- 定位：**每次发布照着从上往下走一遍**。它回答"发什么、发前查什么、怎么发、发完怎么确认、坏了靠什么恢复"。
- 配套四件套（各司其职，别混用）：

| 工具 | 什么时候用 |
|---|---|
| **本文件** | 每次发布，按 §一 → §六 顺序走 |
| `scripts/verify-project.sh` | §二 的门禁：一条命令回答"这个版本现在能不能发" |
| `scripts/db-snapshot.sh` | §五 的数据备份：发布前打一份可还原的快照 |
| `ROLLBACK.md` + `scripts/rollback-drill.sh` | 出事时（手册）/ 平时练兵（演练脚本） |

> 一句话原则：**发布 = 一次可逆的操作**。做之前先确认"退得回去"（§五），做之后立刻证明"真的上去了"（§四）。

## 一、版本标记（发布前先把名字定死）

"v1.0"不是随手写的字符串，它是**回滚时唯一的引用名**。所以要三处对齐：

| 标记 | 落在哪 | v1.0 的值 |
|---|---|---|
| **Git tag** | `git tag -a vX.Y -m "…"` | `v1.0` → 提交 `14f36b6` |
| **页面上的版本标识** | `frontend/index.html` 底部 `#app-ver` | 「自律计划 **v1.0** · 2026-10-13」 |
| **产物指纹** | tag 提交里 `frontend/index.html` 的 md5 + 字节数 | `dc163380cc2800af74cba9c40a2c8984` · 206272 B |

**为什么页面要有一行可见的版本标识**：静态托管的回滚没有版本列表、也没有 UI 提示，线上到底是哪一版**肉眼看不出来**。有这一行，回滚演练的"退回旧版"才有观测点 —— 标识消失 = 退成功了（`ROLLBACK.md` §二）。

**版本号怎么定（本项目约定）**：

| 变更性质 | 版本号 | 例子 |
|---|---|---|
| 新增功能 / 接口 / 页面板块 | 次版本 +1（v1.1） | Day 22 加改删接口 |
| 只修 bug / 只改文档 / 只改样式 | 修订号 +1（v1.0.1） | Day 24 修 favicon 404 |
| **破坏性变更**（删接口、改字段名、翻数据结构） | 主版本 +1（v2.0） | 至今没有 |

> 契约 §1.8 明确 `offline` 字段"只新增不删除"—— 就是为了让每次发布都停在次版本，不需要主版本跳跃。

## 二、发布前验证项（门禁 + 人工三项）

### 2.1 门禁：一条命令

```bash
cd <仓库根>
bash habit-tracker/scripts/verify-project.sh release-gate.txt
echo "退出码=$?"        # 必须 0
```

**通过标准**：退出码 **0**（0 个 ✗）；`release-gate.txt` 里「自证」组必须全 ✓。
**不过怎么办**：证据文件里每条 ✗ 都写了对应卡点，按 `FLOW-TEST.md` §五 的四步协议处理；**有 ✗ 一律不发**。

七组检查各自在验什么（详细判据见 `skills/verify-project/SKILL.md`）：

| 组 | 验什么 | 不过的典型原因 |
|---|---|---|
| **A 安全红线** | 密钥特征 / 敏感文件 / Git 全历史 | `.env` 混进来了、假密钥没清掉 |
| **B 自动化测试** | 前端 jsdom + 云函数自测 | 改了行为没同步测试 |
| **C 线上可达性** | 首页 / health / 图标 / 跨域头 | 环境变量没生效、CORS 缺头 |
| **D 静态资源** | 引用完整性 + 线上可达 + 重复检测 | 引用了没上传的图 |
| **E 数据新鲜度** | 库内最后一天 vs 今天 | 演示会开天窗 |
| **G 踩坑复验** | 跨域预检 / 真读库 / 错误分级 / 幂等 / 软删除 | 历史踩过的坑又踩了 |
| **F 仓库状态** | 工作区干净 / 真的推上去了 | 忘了 push、忘了 commit |

> ⚠ 先看「自证」组：那组不过，说明**检查本身失灵**，后面所有 ✓ 都不可信。

### 2.2 人工确认三项（脚本查不了的）

| # | 项 | 怎么确认 | 不过怎么办 |
|---|---|---|---|
| 1 | **演示数据新鲜** | `verify-project.sh` E 组会报"库内最后一天"。落后就 `bash … db/seed-shift.sql` 平移（**幂等**，隔天必须重跑） | 落后 1 天以上 → 先平移再发 |
| 2 | **发布说明写好** | 一句话说清"这版多了什么"，写进 §六 记录表 | 写不出来 = 这版没内容，别发 |
| 3 | **截图准备好** | 按课程要求的截图项，发布后浏览器里截（提前想好要截哪几屏） | — |

## 三、发布步骤

> 命令都在**仓库根**执行；`MSYS_NO_PATHCONV=1` 与"关沙箱"是 Windows 环境的规定动作（`ROLLBACK.md` §六-2 记了不加会静默失败）。

```bash
# ── 第 0 步：备份（§五）—— 先能退回去，再往前走 ──────────────
bash habit-tracker/scripts/db-snapshot.sh          # 数据快照，落在 db/backups/
git status -sb                                     # 代码：工作区必须干净

# ── 第 1 步：确认本地 = 远程，且东西都推上去了 ──────────────
git log --oneline -3
git ls-remote origin refs/heads/main               # 与 git rev-parse HEAD 比对

# ── 第 2 步：打 tag（发布点定名）────────────────────────────
git tag -a v1.0 -m "自律计划 v1.0 正式发布 —— 前端 <字节数>B md5 <指纹>"
git push origin main v1.0
#   ⚠ push 无输出/报 rejected ≠ 失败：必须 git ls-remote origin refs/tags/v1.0 复核

# ── 第 3 步：部署云函数（只在改了 cloudfunctions/ 时做）────────
export MSYS_NO_PATHCONV=1
tcb fn deploy api --env-id habit-tracker-d9gh0mjel767ff0d2 --force

# ── 第 4 步：部署前端 ──────────────────────────────────────
tcb hosting deploy habit-tracker/frontend --env-id habit-tracker-d9gh0mjel767ff0d2

# ── 第 5 步：发布后验证（§四）───────────────────────────────
```

### 部署顺序：前后端谁先谁后

| 这次改了什么 | 顺序 | 为什么 |
|---|---|---|
| 只改前端（调用已有接口） | 只发前端 | v1.0 就是这种 |
| 只加后端、前端没动 | 只发云函数 | 新接口是旧接口的超集，旧前端不受影响 |
| 前端要用新接口 | **先云函数，后前端** | 反了会在部署间隙出现"前端调不存在的接口" |
| 破坏性变更（删接口 / 改字段名） | 三拍：前端兼容版 → 云函数 → 前端收紧 | 本项目至今没做过，做之前先按 `ROLLBACK.md` §四 演练 |

### 部署耗时参考（v1.0 实测）

| 动作 | 耗时 |
|---|---|
| `tcb hosting deploy` 前端 | **6s** |
| 回滚演练里的一次回退部署 | 4s |
| 恢复一次 | 5s |
| `verify-project.sh` 全量门禁 | 约 2~3 分钟（含 jsdom + 云函数自测 + 联网检查） |

## 四、发布后验证（三口径 + 人工）

```bash
SITE="https://habit-tracker-d9gh0mjel767ff0d2-1499348397.tcloudbaseapp.com"
API="https://habit-tracker-d9gh0mjel767ff0d2.service.tcloudbase.com/api"

# ① 首页可达
curl -s -o /dev/null -w "HTTP=%{http_code} size=%{size_download}\n" -H "Cache-Control: no-cache" "$SITE/"

# ② 线上真的是这一版：指纹 + 版本标识（两个口径都要看）
curl -s -H "Cache-Control: no-cache" "$SITE/" | md5sum     # 应 = §一 表里的指纹
curl -s -H "Cache-Control: no-cache" "$SITE/" | grep -o 'v1\.0'

# ③ 后端真读库（不要只打 /health —— 它是硬编码返回，环境变量坏了照样绿）
curl -s "$API/health"
curl -s "$API/day?date=<库里最新的一天>"
```

| 检查 | 通过标准 | 不过怎么办 |
|---|---|---|
| 首页 HTTP | 200，字节数与本地一致 | 看完整部署输出 → 再怀疑 CDN 缓存（等 1 分钟重打） |
| 线上指纹 | **= 本地 = tag 里那份** | 三方有一方不同 → 部署没生效或工作区有未部署改动 |
| 版本标识 | `v1.0` 出现在页面里 | 没出现 = 部署的是旧产物 |
| `favicon.png` | 200（每个访客的控制台都靠它不报 404） | Day 24 修过，回退时容易忘 |
| `/api/health` | `{"ok":true,…}` | 云函数没部署成功 |
| `/api/day` | `code:0` 且真返回数据 | **环境变量 / 数据库连接问题**（health 查不出这类） |

**人工一项**：用**无痕窗口**打开站点链接（跨过 CloudBase 的"确定访问"首次提示页），确认页面渲染正常、底部版本标识可见 —— 这是要交截图的那一屏。

> 发布后**再跑一次门禁**更稳：`bash habit-tracker/scripts/verify-project.sh`。此时工作区干净，F 组也应该全绿。

## 五、代码与数据备份方式

### 5.1 代码备份

| 手段 | 具体做法 | 可靠性 |
|---|---|---|
| **Git 本地仓库** | `git log` / 每笔提交都在 | 单机故障即丢 |
| **GitHub 远程** | `git push origin main` | 主力备份；**每次发布必须确认已推送** |
| **发布锚点** | `git tag -a vX.Y` + push tag | 回滚的唯一定位手段（托管侧无版本管理） |
| **产物指纹** | 记下 `frontend/index.html` 的 md5 + 字节数 | 用来判断"线上到底是哪一版" |

**不需要另存一份前端快照**：Git 提交里存的就是**原始字节**，`git show v1.0:habit-tracker/frontend/index.html` 取回来与线上逐字节相同（v1.0 实测指纹一致）。
⚠ 取历史产物**必须用 `git show`**，别用 `git archive` —— 后者受 `core.autocrlf=true` 影响会把 LF 改成 CRLF，md5 对不上（`ROLLBACK.md` §六-3）。

### 5.2 数据备份

数据库里是**唯一无法从代码重建**的东西（打卡记录、心情）。发布前必打快照：

```bash
bash habit-tracker/scripts/db-snapshot.sh          # 导出 → habit-tracker/db/backups/<时间>.sql
bash habit-tracker/scripts/db-snapshot.sh --list   # 看已有快照
RESTORE=habit-tracker/db/backups/<时间>.sql bash habit-tracker/scripts/db-snapshot.sh   # 从快照恢复
```

| 手段 | 覆盖范围 | 状态 |
|---|---|---|
| `scripts/db-snapshot.sh` | 两表全量 → 可回放的 INSERT SQL | ✅ **实测可还原**（还原到克隆表后逐行指纹与原表一致） |
| `db/seed.sql` + `db/seed-shift.sql` | 只覆盖演示种子数据 | ✅ 可重建基线，但**不含用户真实记录** |
| CloudBase 控制台数据回档 | 整库时间点回档 | ⚠️ **未验证**（免费版是否支持该能力没试过） |
| `pg_dump` / `tcb db backup` | — | ❌ 用不了：前者需数据库直连串且本机无客户端，后者**是 MySQL 专用**，本项目是 PostgreSQL 环境 |

**三条硬规则**：
1. **快照不入库**：`habit-tracker/db/backups/*.sql` 已写进 `.gitignore`（仓库公开，数据一旦提交就永久留在历史里）。目录靠 `.gitkeep` 保留。
2. **恢复到非空表会主键冲突失败** —— 这是**有意的保护**（不静默覆盖线上好数据）。要覆盖先手工清表，见 `ROLLBACK.md` §五。
3. **恢复过 `checkins` 之后要重设自增序列**，否则下一条插入会撞已用过的 id：
   `SELECT setval(pg_get_serial_sequence('checkins','id'), (SELECT max(id) FROM checkins));`

### 5.3 备份时机

| 时机 | 做什么 |
|---|---|
| 发布前 | 代码确认已 push + 打数据快照 |
| 准备改真库数据前（如跑 `seed-shift.sql`、手工 UPDATE） | 先打快照 |
| 演示前 | 跑一次**只读**的真实性检查（`verify-project.sh` E 组 + `core-flow-check.sh`） |

## 七、出事了怎么办

**不要在这里找答案** —— 直接翻 `ROLLBACK.md`：

1. 先看 §一「什么情况必须回滚」判断表（**数据问题回滚版本没用**）；
2. 静态托管 → §三（**已实测**，四步 + 耗时）；云函数 → §四（只备查，未演练）；
3. 数据 → §五 + 本文件 §5.2 的恢复命令；
4. 演练记录格式（每步做了什么 / 耗时 / 结果）→ `ROLLBACK.md` §七 模板。
