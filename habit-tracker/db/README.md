## 一、今天要掌握的问题：两张表分别存什么？靠哪个字段关联？

### `plan_days` —— 计划日（**一天一条**）

存的是「**哪一天**」这件事本身：**日期 + 当天心情**。

一天只允许一条，这个约束不是写在代码里的，而是**数据库主键物理保证**的：`PRIMARY KEY (uid, date)`。谁想给同一天插第二条，数据库直接报错。

### `checkins` —— 打卡项（**一天多条**）

存的是「**那一天要做/已做的事**」：待办内容、安排时间、四象限、完成状态。也就是今天页下面那个待办列表。

### 靠哪个字段关联？—— **`date`**

```
plan_days                          checkins
┌──────────────────────┐           ┌──────────────────────────┐
│ uid   date     mood  │           │ id  uid   date    text    │
│ seed… 2026-10-01 平静 │──┐        │ 5   seed… 2026-10-01 晨跑  │
└──────────────────────┘  │        │ 8   seed… 2026-10-01 整理  │
                          │        │ 3   seed… 2026-10-01 打电话│
     同一天 ──────────────┴───────→│ 1   seed… 2026-10-01 复盘  │
                                  │ 4   seed… 2026-10-01 泡脚  │
                                  └──────────────────────────┘
```

准确说关联用的是 **`(uid, date)` 两个字段**：`uid` 保证"是同一个人"，`date` 保证"是同一天"。只按 `date` 关联，多用户下会把别人的数据串进来。

`verify.sql` 的"验证 3"就是把这两张表按 `(uid, date)` 连起来查——那正是**今天页首屏的数据形状**：左边提供"这天 + 心情"，右边提供"这天的打卡项和完成情况"。

> 这个关联不是外键，是**逻辑关联**（为什么见 §三 设计取舍 1）。

## 二、字段类型为什么这么选（余力加练）

### 通用两条

- **`uid` 用 `TEXT`**：它来自 CloudBase 匿名登录生成的字符串，不是我们产生的数字序号。硬要用数字会逼着做一层映射，纯属自找麻烦。
- **时间戳用 `TIMESTAMPTZ` 而不是 `TIMESTAMP`**：`TIMESTAMPTZ` 存的是"绝对时刻"，带上时区信息。用户换个时区打开、或者服务器时区变了，`created_at` 的含义不会跟着漂。`TIMESTAMP`（不带时区）在跨时区场景是经典的坑。
- **`DEFAULT now()`**：让"什么时候建的"由数据库负责，避免依赖函数里传的时间（客户端时钟可以被随便改）。

### `plan_days`

| 字段 | 类型 | 为什么 |
|---|---|---|
| `uid` | `TEXT` | 见上 |
| `date` | **`DATE`** | 我们要的是「2026 年 10 月 1 日」这个**日历上的日子**，不是某个时刻——`DATE` 正好，而且比较、分组、排序都直观（`WHERE date = DATE '2026-10-01'`）。用 `TIMESTAMP` 会引入"几点算今天"的歧义，等于把时区问题重新请回来 |
| `mood` | `TEXT` + `CHECK` 枚举 | 心情只有 5 个固定取值（sad/blue/calm/cozy/joy）。PostgreSQL 本来有 `ENUM` 类型，但它**加值要 `ALTER TYPE`、删值几乎不可能**；用 `TEXT + CHECK` 改起来就是改一句约束，更灵活。**可空**是因为"今天还没打卡"是正常状态，不是错误 |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | 见上。`updated_at` 专门用来记"心情被改过的时间" |

### `checkins`

| 字段 | 类型 | 为什么 |
|---|---|---|
| `id` | **`BIGSERIAL`** | 自增整数主键，接口路径 `:id` 用的就是它。用 `BIGSERIAL` 而不是 `SERIAL`：将来数据涨到 21 亿条以上不会溢出，现在多花几个字节而已。不用 UUID 是因为**人会看这个 id**（调试、日志里一眼能读懂），且单库自增够用 |
| `date` | `DATE` | 同 plan_days |
| `text` | `TEXT` + 长度约束 | 内容长度不定，`TEXT` 最合适（PG 里 `VARCHAR(n)` 性能上并无优势）。上限用 **`CHECK (char_length(text) <= 60)`** 而不是 `VARCHAR(60)`：长度是**业务规则**，写成 `CHECK` 将来想放宽只需改约束；写成 `VARCHAR(60)` 改起来要 `ALTER TABLE ... TYPE`，还可能锁表。另外 `char_length` 按**字符**算，中英文都按"字"数，符合直觉 |
| `time` | `TEXT` 而非 `TIME` | 前端存的是 `'HH:mm'` **纯字符串**（用户"安排几点做"，不是"某个时刻"）。用 `TIME` 类型会被服务器按 24 小时制规范化、还可能带上秒和时区后缀，回给前端就不是原样了。用 `TEXT` + 正则约束 `^([01][0-9]\|2[0-3]):[0-5][0-9]$`，既管住格式又保持原样传递。**可空** = 没安排具体时间（前端就是这么用的） |
| `quad` | `TEXT` + `CHECK` 枚举 | 同 `mood` 的理由。可空 = 未分类 |
| `done` | `BOOLEAN NOT NULL DEFAULT FALSE` | `NOT NULL` 很重要：三态（true/false/null）会让每个查询都要防 null，白白多一层心智负担。默认"没完成"最符合直觉 |
| `done_at` | `TIMESTAMPTZ`，可空 | 只有完成才有值。并用约束**强制和 `done` 一致**：打了勾必须有完成时刻、没打勾必须为空——免得出现"完成了但不知道什么时候完成的"这种半截数据 |
| `sort` | `INTEGER` | 同一天内的排序位。为什么不用 `created_at` 排序？因为产品有"移动待办"功能，顺序是**用户手动调过的**，不是插入顺序 |

### 索引

```sql
CREATE INDEX checkins_uid_date_idx ON checkins (uid, date);
```

`plan_days` 不用额外建索引——主键 `(uid, date)` 本身就是索引。`checkins` 的主键是 `id`，所以按"某人的某天"查会全表扫描，必须补一个 `(uid, date)` 索引。这个顺序也有讲究：`uid` 在前，因为每个查询都带 `uid`（安全要求），`date` 在后做区间筛选。

## 三、设计取舍（刻意没做的两件事）

### 1. 没有给 `checkins` 加指向 `plan_days` 的外键

产品的真实用法是"用户直接加一条待办"，**很可能一整天都不去点心情**。如果加了外键，加待办之前就必须先有 `plan_days` 那一行，等于凭空多一步，还会让 Day 17 写接口变复杂。

所以两张表是**逻辑关联**（靠 `(uid, date)`），一致性由服务层保证。将来若确认"每天首次写入必先 upsert plan_days"，再补外键也很快（一条 `ALTER TABLE`）。

### 2. 没有建统计表

完成数、连续天数、心情分布、月度报告一律**现算不存**（PRD 原则），由 `report` 接口用 `SELECT` 聚合直接算。这样永远不会出现"统计表和真实数据对不上"的经典问题。

## 五、本地无 Postgres 时怎么验证（我们实际用的办法）

本机没装 PostgreSQL，所以用 **pglite**（真正的 PostgreSQL 编译成 WebAssembly，跑在 Node 里）把三个脚本真跑了一遍：

- `schema.sql` 跑两遍 → 不报错，建出 `checkins` / `plan_days` 两张表
- `seed.sql` 连跑三遍 → plan_days 稳定 7 行、checkins 稳定 8 行（**幂等成立**）
- 6 条约束拦截测试（非法心情、`25:99`、打勾却没时刻、同人同日两条、空内容、超 60 字）→ **全部被数据库挡住**

结果：**16 项断言全过**。这不能替代在真实 CloudBase 上执行，但能证明 SQL 语法与约束逻辑是对的，避免在控制台里反复试错。

## 六、种子数据的 uid 说明（重要）

种子数据统一用 `uid = 'seed-demo-user'`（编造的账号）。

**Day 17 现状（接口已通，但登录还没接）**：云函数取 `uid` 的顺序是
① `context.userInfo.uid`（平台注入的登录身份，接上匿名登录后自动生效）→ ② 函数环境变量 `DEMO_UID`。
当前环境变量 `DEMO_UID` 就设为 `seed-demo-user`，所以**接口读到的正是这批种子数据** —— 这是刻意的，
这样"接口能读出数据"与"数据来自真库"两件事可以分开验证。

等 Day 18 接上匿名登录、拿到你自己的 `uid` 之后，想让自己的账号看到这批数据，执行一次：

```sql
UPDATE plan_days SET uid = '<你的真实 uid>' WHERE uid = 'seed-demo-user';
UPDATE checkins  SET uid = '<你的真实 uid>' WHERE uid = 'seed-demo-user';
```

> ⚠️ 隐私红线（AGENTS.md R6）：仓库是 public 的，**种子数据里的心情、待办全部是编的**，永远不要把真实的个人内容写进 `seed.sql`。
