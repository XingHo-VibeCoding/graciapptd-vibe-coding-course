# 卡点分诊与复验（试用闭环的后半段）

> **什么时候用它**：试用记录填完（`record-sheet.md`）之后。它负责三件事：
> **① 从一堆卡点里选出一条来修 → ② 把选中的那条写成给 AI 的修复指令 → ③ 修完给用户一个最小复验任务**。
>
> **和 `FLOW-TEST.md` §五 的分工**（别互相替代）：
> - 本文件 = **修哪条**（选择）+ 怎么下指令 + 修完怎么验；
> - `FLOW-TEST.md` §五 四步协议 = **怎么修**（原因排序 → 验证方法 → 修复方案 → 回归清单）。
> - `FLOW-TEST.md` §四 = 卡点的**记录格式**（现象 / 复现步骤 / 报错原文 / 已尝试动作），
>   本文件 §三 直接引用它，不另立格式。
>
> **一条铁律**：**一次只修一条**（AGENTS R1）。改三处再一起验，等于三处都验不清。

---

## 一、分诊：先算，再排序

### 第 0 步 · 三道硬门槛（过不了就别进修复流程）

| 门槛 | 过不了怎么办 |
|---|---|
| **能复现吗？**（换个设备 / 再走一遍还能撞上） | 记「**未能复现**」，挂着，先别修 —— 修不了看不见的东西 |
| **有证据吗？**（§四 四段齐全，尤其"报错原文"是原样抄的） | 打回去补证据。**不接受转述**：没有 Console 原文 / 脚本输出 / Request URL 的，先补 |
| **在我能改的范围内吗？** | 平台限制 / 需备案 / 需付费的 → 直接落到 **P2 已知边界**，并写进 `task-card.md` 第 0 步**提前告知**（告知 ≠ 修好，但能消掉"被坑"的感觉） |

**再问一句：这是缺陷还是需求？**

| | 定义 | 走哪条路 |
|---|---|---|
| **缺陷** | 本该能用，却不能用 / 用错了 | 进下面的 P0/P1 排序 |
| **需求** | 本来就还没做（如"没有改文字的编辑功能"） | **P2 + 待做清单**。★ 不要在修 bug 的轮次里顺手加功能 —— 那会让"这次修了什么"说不清 |

### 第 1 步 · 定级（满足任意一条就取该级，**不因为"影响面小"而降级**）

| 级别 | 判据 | 本项目已见过的例子 |
|---|---|---|
| **P0 · 当天必修** | ① 核心链路**走不下去** ② 数据错乱 / 看起来丢了 ③ 泄露密钥、隐私或**可被利用的内部信息** ④ 把用户的东西弄没的路径 | 首页"今天"空白（新人不知道干什么）；`/api/nope` 的 404 白送整张路由表 + 云函数版本号 |
| **P1 · 本次修** | ① 走得过去，但**每一步都要猜**或绕 ② **2 个人**在同一处卡住 ③ 一次误触就丢数据（没有二次确认） | 找不到"怎么标记完成"（核心动作要猜）；删除没有确认框 |
| **P2 · 记录在案** | ① 平台限制改不了 ② 个人偏好（有人喜有人厌） ③ 已有替代路径 ④ 只出现 1 次且**他自己解决了** | 首访的腾讯云「风险提醒」中间页；"暂不支持改文字" |

> ⚠ **最容易被自己骗的一处**：把"我改不了"说成 P2。
> 判 P2 的前提是**真的不在可改范围内**（平台文档写明 / 需要备案 / 需要付费），
> 而不是"改起来麻烦"。改起来麻烦的是 P1。

### 第 2 步 · 平级怎么选（tie-break，按顺序比）

1. **改一处能消掉多条反馈**的优先（一份改动换几条反馈，性价比最高）；
2. **所有新用户都会撞** > 只影响某种设备/某种浏览器；
3. **改动面小**的优先（只改文案 / 一个文件 < 动结构）；
4. 离下次演示 / 发布**更近**的优先。

### 第 3 步 · 输出（照这个格式写一行结论，放进 `record-sheet.md` §七）

```
本次只修 1 条：<卡点>（P0/P1，证据见 §四 卡点N）。
其余 <n> 条：<x> 条写成已知边界并加进脚本第 0 步；<y> 条进待做清单；<z> 条未能复现，挂着。
不修的理由一句话：<…>
```

## 二、为什么常常只修一条（别贪）

- **验证需要干净的对照**：一次改一处，出问题立刻知道是哪处；
- **修 1 条 + 告知 1 条 > 修 3 条 + 沉默 2 条**：用户对"被提前告知"的容忍度远高于"自己撞上";
- **卡点的"根"常常只有一个**：比如"找不到入口"和"以为功能坏了"经常是同一处文案的问题 ——
  所以选的时候优先找**能一次消掉多条**的那处（§一 第 2 步第 1 条）。

## 三、修复提示词模板（直接复制，填空即可）

> 用途：把选中的卡点变成一段**一次就能说清**的指令。缺任何一格，AI 都会替你猜 —— 猜错就返工。

```text
【背景】自律计划（vanilla JS 单文件前端 habit-tracker/frontend/index.html + CloudBase 云函数
habit-tracker/cloudfunctions/api/）。本次是第三方试用后的修复轮，只做这一条，不许顺手改别的。

【目标】一句话：<要修成什么样>

【现象与证据】（原样贴，别转述）
- 现象：
- 复现步骤（从打开链接开始）：
- 报错原文（Console / 脚本输出 / 屏幕文字）：
- 他自己的尝试：
- 证据文件：<record-sheet.md §四 卡点N / 截图路径 / 命令输出>

【这次不许动的东西】
- <例：不许改接口契约、不许改软删除逻辑、不许动配色变量>
- 不许新增功能（那是需求，不在本轮）

【完成标准】
1. 主症状消失：<可判定的判据，例：新人不用猜就能找到"标记完成"的入口>
2. 回归：<原来就能用的仍然可用，例：六环自检 0 失败 / 前端 417 条断言全绿>
3. 边界不变：<例：公开 URL 仍 200、行数仍 7/9、无新增路由>

【证据要求】
- 跑什么、贴什么输出（例：bash habit-tracker/scripts/verify-project.sh 的输出 + 失败项详情）
- 修前 / 修后各一条证据，能对比

【收尾】列出改动文件清单 → 说明属于哪天任务 → commit（标题 Day N｜一句话；说明两行：改了什么 / 加了什么）→ push → 停下等确认。
```

**填空示例**（拿 §一 的 P0 举例）：

```text
【目标】让新人打开首页就知道今天能干什么 —— 空状态下的引导要指得出下一步。

【现象与证据】
- 现象：首页「今天」是空的（种子数据停在 10-09，落后 6 天），页面只说"今天还没有安排"
- 复现步骤：打开公网链接 → 第 0 步点「确定访问」→ 第 1 步看今日安排
- 报错原文：无报错（屏幕原文："今天还没有安排，写一条试试"）
- 他自己的尝试：点了"或看看示例数据 →"
- 证据文件：self-test 截图 00-firstvisit-midpage.png / drive-user-flow 输出 6 通过 5 失败

【这次不许动的】接口契约、云函数路由、配色变量。
【完成标准】① 首页出现 ≥6 张待办卡片、计数正确 ② 六环自检仍 0 失败 ③ 公开 URL 仍 200、路由数不变
【证据要求】修前后各一条 `drive-user-flow.js --width=390` 输出 + 真库 SELECT 计数
```

## 四、复验最小任务模板（修完给用户 / 试用者）

> 原则：**只测那一条卡点**。别让对方重走全流程 —— 他又不是测试员，
> 而且流程越长，"到底哪一步变好了"越说不清。
> 三条就够：**主任务（测修好的那条）+ 回归一条 + 边界一条**。

```text
【复验 1 · 主任务】<只走那条卡点>
  怎么做：<从打开链接起，最多 3 步>
  预期：<能判定的结果，例：不用问任何人就能完成一次打卡>
  怎么算通过：<他做到了 / 没说"找不到" / 没有再回头看我>

【复验 2 · 回归】<原来就能用的那件事>
  怎么做：<例：刷新页面，刚写的还在>
  预期：<不变>
  怎么算通过：<数据还在、没报错>

【复验 3 · 边界】<不该变的没变>
  怎么做：<例：打开公网链接、看今天有几条>
  预期：<行数/内容与修前一致（plan_days 7 / checkins 9）>
  怎么算通过：<一致>

【记录方式】每条写：预期 / 实际 / 通过与否 / 证据（截图或命令输出）
【仍然卡住怎么办】照 FLOW-TEST.md §四 记四段，回 §一 重新定级 —— 不要当场再改一轮
```

## 五、示范：拿已记录的三条跑一遍规则（Day 27 的既有发现）

> 这三条是 `trial/selftest-record.md` 里的真实发现，拿它们验一下上面这套判据**跑得通、不虚设**。

| 卡点 | 三道门槛 | 缺陷/需求 | 判级 | 依据（对照 §一 第 1 步） | 实际处置 |
|---|---|---|---|---|---|
| 首页「今天」空白（种子停在 10-09） | 可复现 ✓ / 有证据 ✓ / 可改 ✓ | 缺陷（数据过期） | **P0** | 判据①核心链路走不下去 + ②看起来"没数据" | ✅ 已修：跑 `seed-shift.sql` 平移 |
| `/api/nope` 404 泄露路由表 + 版本号 + 路径回显 | 可复现 ✓ / 有证据 ✓ / 可改 ✓ | 缺陷 | **P0** | 判据③泄露可被利用的内部信息（★不因"影响面小"降级） | ✅ 已修：404 收口 + 3 处断言反转 |
| 首访先撞腾讯云「风险提醒」中间页 | 可复现 ✓ / 有证据 ✓ / **不可改 ✗** | — | **P2** | 平台限制，官方文档：移除唯一途径 = 绑自定义域名（需 ICP 备案） | ✅ 写成已知边界 + 脚本第 0 步提前告知 |
| （虚构）"以为能改待办文字，找不到编辑" | 可复现 ✓ / 有证据 ✓ / 可改 ✓ | **需求**（功能本就没做） | **P2** | §一 第 0 步"缺陷 vs 需求" → 进待做清单 | 记录在案，不在修复轮顺手加 |

**这套规则跑下来的两个可检验结论**：
1. 三条既有发现分别落在 P0 / P0 / P2，**没有一条卡在"说不清该不该修"上** → 判据可判定；
2. 唯一的 P2 是**真的不可改**（有官方文档背书），不是"改起来麻烦" → 没有把偷懒判成 P2。
