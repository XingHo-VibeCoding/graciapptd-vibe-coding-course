## 一、技术路线（一句话 + 理由）

> **纯前端三件套（HTML + CSS + JavaScript）+ 浏览器 localStorage 存储，不设后端，不引入框架。**

### 为什么是它（逐条理由）

| 决策 | 选择 | 理由 | 放弃的备选 |
|------|------|------|-----------|
| 语言层 | 原生 HTML/CSS/JS | ① 零基础 28 天内必须能看懂全部代码；② 打卡/卡片/时间轴都是"渲染 + 存取"逻辑，无复杂计算，框架收益低 | Vue/React：能力溢出，且学习成本会吃掉第 2、3 周全部开发时间 |
| 存储 | localStorage | ① 数据天然在用户自己浏览器里，隐私零成本；② 无后端 = 无服务器费用、无鉴权、无接口调试 | 后端+数据库：PRD 已把登录/多用户列为后续，MVP 单机即够 |
| 形态 | 一个页面（3 个视图切换） | PRD 的三区块（今日/思考/我的）本质是同一份数据的三个视图，单页切换最省 | 多页面跳转：3 个 HTML 会带来重复导航代码 |
| 部署 | 静态托管（GitHub Pages 候选） | 纯静态文件可直接托管，仓库流程已跑通 | 服务器部署：无后端就不需要 |

### PRD 三个开放问题的裁定（Day 5 必须定）

**Q1：一天的"零点"在哪？**
→ **采用本机自然日零点（00:00）**。凌晨 1 点打勾算新的一天。
理由：实现最简单、用户直觉一致（日历也是零点翻页）；"凌晨 4 点前算前一天"是夜猫子场景优化，MVP 用户是自己，出现痛点再改（改动点只在取日期的函数，成本可控）。

**Q2：localStorage 够用吗？**
→ **够用，且富余极大**。估算：每日 10 条待办 + 1 条心情 + 2 张卡片 ≈ 1KB/天；localStorage 上限约 5MB ≈ **可用 13 年以上**。结论：不做迁移设计，但存储模块统一走一个读写函数（见数据流图），将来换 IndexedDB / 云端只改这一个模块。

**Q3：每日一问怎么随机？**
→ **洗牌法**：题池 30 题打乱成队列，每天弹队首，当天最多"换一个"3 次即顺延取队列下一题；队列用完重新洗牌。存"已出题索引列表"即可，无需存随机种子。

## 二、数据流图（核心：数据从哪来、到哪去）

```
┌──────────┐  用户输入          ┌─────────────┐  JSON 序列化     ┌───────────────┐
│ 用户操作  │ ───────────────→  │ 事件监听     │ ──────────────→ │ localStorage  │
│ (打勾/写  │                   │ (main.js)   │  统一写入口      │ (浏览器本地)   │
│ 卡/选心情)│                   │  更新数据模型 │  saveData()     │               │
└──────────┘                   └─────────────┘                  └───────┬───────┘
                                                                      │ JSON 反序列化
                                       读取                          │ 统一读入口
┌──────────┐  渲染结果          ┌─────────────┐  loadData()          │
│ 用户看到  │ ←───────────────  │ 页面渲染     │ ←──────────────────┘
│ (时间轴/  │                   │ (时间轴/卡片  │
│ 卡片/月历)│                   │ /月历视图)   │
└──────────┘                   └─────────────┘

数据流一句话：用户输入 → JS 更新数据模型 → 存 localStorage（落盘）；
              页面打开 → JS 从 localStorage 读数据 → 渲染给用户看。
```

**三条铁律**（写代码前先立，防止后面乱）：

1. **所有读写只走一个模块**：页面代码永远调 `loadData()/saveData()`，不直接碰 `localStorage` API——将来换存储只改一个文件
2. **先改数据、再渲染**：任何操作都是"更新模型 → 存盘 → 重新渲染"，不允许跳步（跳步 = 数据和画面不一致的经典 bug）
3. **统计现算不存**：完成数、连续天数、心情分布、报告，每次从原始记录计算（PRD 既定原则）

## 三、数据模型（localStorage 里的四把钥匙）

```
localStorage 键               值（JSON）
─────────────────────────────────────────────────────────────
zl.todos      →  [ { date:"2026-09-20", text:"晨跑", time:"07:00", done:true }, ... ]
zl.moods      →  [ { date:"2026-09-20", mood:"smile" }, ... ]   // smile/calm/cry
zl.notes      →  [ { datetime:"2026-09-20 09:30", text:"...", fromQuestion: true }, ... ]
zl.profile    →  { name:"自律的你", theme:"warm" }
```

> 统一前缀 `zl.`（自律）：将来浏览器 DevTools 里一眼能认出是我们家的数据。

## 五、非功能要求（从 PRD 继承，技术侧确认）

| 要求 | 技术侧做法 |
|------|-----------|
| 打开 ≤ 3 秒能操作 | 无外部依赖（无 CDN、无框架），加载即就绪 |
| 刷新不丢数据 | 每次操作立即 saveData()，不搞"定时批量保存" |
| 3 套主题 | CSS 自定义属性（变量）+ body 上一个 class 切换 |
| 无登录无付费无推荐 | 无后端 = 天然成立 |

## 六、方案变化影响表（余力加练：改需求时动哪些文件）

| 如果方案变化… | 受影响文件 | 影响范围 |
|---------------|-----------|---------|
| 改配色/主题 | `style.css` | 仅样式，零逻辑风险 |
| 加一种心情表情（如"疲惫"） | `main.js`（心情模块）+ `style.css` | 小：数据模型 mood 加一个枚举值，月历渲染自动兼容 |
| 待办支持拖拽改时间 | `main.js`（时间轴模块） | 中：交互逻辑重写，渲染可复用 |
| 每日一问改成 AI 出题 | 新增后端或 API 调用 + `main.js` | 大：引入网络依赖与密钥管理（本期明确不做） |
| 存储 localStorage → 云端 | 只改 `main.js` 的数据模块（loadData/saveData） | 小（因铁律 1）：其他代码无感知；但要加后端 + 鉴权 |
| 增加第四个页面（如"统计"） | `index.html` + `main.js` + `style.css` | 中：三个文件都要动，但已有模式可复制 |
| PRD 改验收标准 | `PRD.md` → 通常连带 `TECH_DESIGN.md` | 文档先行：先改文档再改代码 |

> 这张表的隐藏结论：**把"存储"和"逻辑"隔离开（铁律 1）是全表里最划算的投资**——它让第 5 行那种"换存储"的大变化变成小改动。

## 七、风险与已知限制（诚实清单）

| # | 风险 | 应对 |
|---|------|------|
| 1 | localStorage 可被用户手动清浏览器数据时误删 | MVP 接受（数据是自己的）；二期做导出备份 |
| 2 | 换浏览器/换电脑数据不跟着走 | PRD 已明确云同步列后续 |
